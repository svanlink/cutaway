## Findings, ranked by money at risk

### 1. Restore cannot open a single backup that exists on this Mac — silently
`StorePath.swift:72` · `AppModel.swift:55-57`

`stagePendingRestore` looks for a file named exactly `target.lastPathComponent` — now `billing.store`. The real folder holds twelve backups and **none of them contains a `billing.store`**:

```
billing-20260823-122952 … billing-20260905-114410   →  default.store, -wal, -shm, manifest.json
billing-20260906-121035 … billing-20260907-175302   →  timex.store,   -wal, -shm, manifest.json
```

So: Settings › Data › Restore… rejects every folder in its own default directory with "That folder does not hold a Cutaway backup." And the automatic damaged-store restore (`AppModel.swift:93`) throws into `catch { NSLog(…) }` at line 96 — no banner, no notice — then opens the damaged store anyway. The five `default.store` folders are the ones that recovered the data in the 2026-09-06 incident. They are unreachable through the feature README already advertises as shipped.

Smallest fix: in `stagePendingRestore`, resolve the source by content, not name — the single `*.store` in the folder — and copy it to `pendingRestoreURL`. Two lines. Add the pre-1.3.2 name to `holdsCutawayTables`' caller, not to the schema check (that part is already right).

### 2. Harness runs back their throwaway store into the real folder, and are evicting real history
`AppModel.swift:55-57` vs `StorePath.swift:14-23`

`StorePath.url()` quarantines on `CUTAWAY_DATA_DIR`. `AppModel.backupsDir` is a hard `static let` on the real `Application Support/Cutaway/Backups`, and the backup block is gated on `ScenarioMode.isActive`, which is `CUTAWAY_SCENARIO != nil` only (`Prefs.swift:50`). A UI test sets `CUTAWAY_DATA_DIR` and nothing else — so it backs up `<tmp>/timex.store` into the owner's real backup folder. `billing-20260907-175302` was written by the UI test run in this session, 732 KB of nothing.

Seven of the twelve folders are now harness junk, and they occupy the **entire** keep-newest-7 bucket. The five real backups survive only on the 30-day daily rule; `billing-20260823` is evicted on 2026-09-22. This is the 2026-08-23 incident recurring through a different door, and it also makes `StoreBackup.newest` — the source for automatic restore — point at a test store.

Smallest fix: `static var backupsDir { StorePath.url().deletingLastPathComponent().appendingPathComponent("Backups") }`. The quarantine already exists; use it.

### 3. Three of the four launch-sequence failures are NSLog-only
`AppModel.swift:83, 87, 96, 100`

Legacy adoption failed, pending restore failed, automatic restore failed, launch backup failed (disk full, folder read-only, `moveItem` name collision) — all four write to `NSLog` and nothing else. `StoreErrorReporter.notice` exists and is already used two lines away on the success path. Concrete: disk 100 % full at launch → `copyItem` throws in `StoreBackup.swift:56` → staging cleaned, error rethrown → line 100 swallows it → the user tracks a month believing "Backups: daily" from Settings, with no backup since the disk filled. Settings even prints `Last backup <date>` from `lastBackup`, which is not advanced on failure, so the only signal is a date that stops moving. Fix: `storeErrors.flag(…)` alongside each `NSLog`, and colour the Settings line when `lastBackup` is older than 48 h.

### 4. Automatic restore trusts the newest backup and never falls back
`AppModel.swift:90-97`

`quickCheckOK` is applied to the live store but never to the backup being restored — `stagePendingRestore` only checks that a `ZPROJECT` table name exists in `sqlite_master`, which a torn file can still answer. And there is no second attempt: if the newest folder fails, the loop ends. Concrete: the store is damaged, the newest backup is the mid-write one from the same incident, restore either fails silently (finding 3) or installs a damaged store; four healthy older backups sit untouched. Fix: iterate `existingBackups` newest-first, `quickCheckOK` each candidate, stop at the first that passes, and say which one in the notice.

### 5. Day-edit anchor clamp is wrong on spring-forward days
`SessionStore.swift:111`

`let dayEnd = dayStart.addingTimeInterval(86_400 - 1)`. Europe/Zurich, 2026-03-29 is 82 800 s long, so `dayEnd` lands at 2026-03-30 00:59:59 and the `min(...)` clamp stops clamping. Concrete: a session split at midnight has `end == 2026-03-30 00:00:00` while belonging to the 29th; the user opens Edit Day for 2026-03-29 and adds 1 h; the zero-span adjustment is written at 2026-03-30 00:00:00, `dayTotals` groups it by `startOfDay(for: start)` onto the **30th**. The 29th does not change, the 30th silently grows, and every retry adds another hour — exactly the failure the comment above the line says it is preventing. Fix: `calendar.date(byAdding: .day, value: 1, to: dayStart)!.addingTimeInterval(-1)`. Note the new `testSplitAcrossDSTJumpKeepsEverySecond` covers `DaySplitter` and looks like DST coverage; it does not touch this path.

### 6. The restore relaunch runs two instances against one store
`SettingsView.swift:193-196`

`createsNewApplicationInstance = true`, then `NSApp.terminate` in the completion handler. Instance 2's `AppModel.init` runs `applyPendingRestore`, which `moveItem`s the live store aside while instance 1 still holds a SwiftData connection on that inode; instance 1 then runs `applicationWillTerminate` → `engine.stop()` → saves the closing session into the orphaned `.replaced-…` file, and `backUpNow` snapshots the *path*, i.e. instance 2's store. The last session before a restore is lost to a file nothing reads again. Fix: terminate first and relaunch from an `atexit`-style helper, or simply drop the auto-relaunch — tell the user to reopen Cutaway.

### 7. Shrinking a day can trim the tracked session instead of the typed one
`SessionStore.swift:103`

`sorted { $0.end < $1.end }` is not stable, and a grow adjustment is anchored at `sessions.last?.end` — the same instant as the session it follows. Concrete: day has 1 h tracked ending 17:00 and a 30 min adjustment at 17:00; shrink the day by 30 min; the loop may trim the tracked half. `adjusted_hours` in the CSV then claims typed time that was tracked, or the reverse. Fix: tiebreak on `isAdjusted` — `sorted { ($0.end, $0.isAdjusted) < … }`, adjustments last, so shrink always eats typed time first.

### 8. A typed adjustment on a past day bills at today's rate
`SessionStore.swift:113-114`

`hourlyRate: project.hourlyRate` — the current one. Add 1 h to a March day worked at CHF 80 after raising to CHF 100: the day becomes 2 h / CHF 180, and `DayTotal.effectiveRate` prints `hourly_rate 90.00` in the CSV — a rate never quoted to anyone. Fix: stamp the adjustment with the day's own `effectiveRate` when the day has sessions.

### 9–10. Litter, not loss
`SettingsView.swift:191` removes only the base pending file on Cancel, leaving `-wal`/`-shm` orphans — cleared on the next stage. `StoreBackup.swift:49-51` leaves `.staging-…` folders on a crashed copy forever; rotation ignores them.

## What is fine, plainly

The clock abstraction is genuinely clean: `now: () -> Date` everywhere in `DetectionEngine`, and the tick delta is `min(max(t.timeIntervalSince($0), 0), 5)` (`:299`) — a backward NTP jump credits zero, a forward one is capped. Midnight force-close (`:190`) and the hard-boundary close on manual/sleep/noProject (`:224`) mean sessions do not span days; `DaySplitter`'s proportional model is only reached by crash records, which is what its invariant comment claims. `CSVExporter` rounds once at printed precision before summing, filters the period inside the exporter, pins POSIX locale *and* `timeZone` on all three formatters, and escapes leading `=+-@`. Rates are stamped at `record` time. Staging-then-rename means a backup killed mid-copy — including a `VACUUM INTO` killed by the logout timeout during the quit backup — can never leave a folder that looks complete. Rotation's two buckets, plus "a name that does not parse is never deleted", is right. The crash snapshot clears only after a successful persist, and an unmatched project name defers rather than inventing a session.

## Release gate for the Invoice quarter

Before a `vX.Y.Z` tag exists, all of these must be true:

1. `-only-testing:CutawayTests` green, `./scripts/smoke.sh "" 3` all-pass on a build stamped today, **and `-only-testing:CutawayUITests` green.** Today it is not; the tag would ship a red gate.
2. `git diff --quiet && git diff --cached --quiet`. `release.sh:60` does `git branch -f main HEAD` — main is moved to the last *commit* while the Release binary was compiled from the working tree. Ship from a dirty tree and the tag and the zip are different programs. There is no such check today. Add it as line 5.
3. `default.profraw` gitignored (it is untracked and unignored right now — one `git add -A` away from the release commit).
4. The restore path exercised by hand once per release: restore the oldest folder in the real Backups dir into a scratch `CUTAWAY_DATA_DIR`, open it, confirm the project and totals. No automation covers this.
5. `codesign --verify --deep --strict` on the **unzipped** artifact, plus one manual right-click-Open on a machine that has never run Cutaway — without notarization the quarantine flow is the whole first-run experience and nothing tests it.

What CI proves: the project generates, the version stamp matches the tag, the unit suite passes on Xcode 26.3, a Release build compiles and ad-hoc signs. What it does **not** prove: the smoke scenarios (README admits `release.sh` is the only path that runs them), the UI tests, that the zip launches, that the cask's sha matches a downloadable asset, and that the tag was produced by `release.sh` at all — `git push --tags` by hand publishes a release and bumps the Homebrew cask having proven only the unit suite. With Homebrew plus a bare zip and no notarization to fall back on, CI must at minimum run `-only-testing:CutawayUITests` and gate on it.

## Arbitration 2026-09-07: store damage and recovery

Both departments diagnosed the same defect. Both prescriptions are incomplete. Ruling
below is binding for the branch; nothing in Sources/ was changed to produce it.

### 1. The damage test

`quickCheckOK -> Bool` is abolished. `StorePath.verdict(_:) -> Verdict` returns one of
`absent`, `usable`, `unreadable(reason)`, `damaged(reason)`, evaluated in this order:

| Condition | Verdict |
|---|---|
| file does not exist | `absent` |
| `sqlite3_open_v2` returns CANTOPEN / PERM / AUTH / BUSY / LOCKED / READONLY / IOERR / FULL | `unreadable` |
| open returns NOTADB or CORRUPT | `damaged` |
| `PRAGMA quick_check` aborts with BUSY / LOCKED / IOERR mid-scan | `unreadable` |
| first `quick_check` row != "ok" | `damaged` |
| quick_check ok, `sqlite_master` holds no tables (covers the 0-byte file) | `damaged` |
| quick_check ok, tables present, no `ZPROJECT` | `damaged` (foreign) |
| quick_check ok, `ZPROJECT` present — **including with zero rows** | `usable` |

Permissions, disk-full and a Time Machine lock are `unreadable`, never `damaged`.
Zero-byte and foreign-schema are `damaged` — architecture's `holdsCutawayTables`
conjunction is upheld, but as a classifier, not as a restore trigger. An empty
*Cutaway* store is `usable`: restoring over a legitimately empty first run is the
2026-08-23 loop in reverse.

Architecture's `cleanShutdown` gate is granted for the `quick_check` page scan only.
Existence, open, and the `sqlite_master` probe are O(1) and run every launch.

### 2. Verdict → action, and consent

**Ruling: the app may never move, replace or overwrite the live store without the
owner saying yes first. No exception, including the automatic path.** Quality wins
this point outright; architecture loses it. The reasons are that the classifier can be
wrong, `.replaced-<stamp>` is not a visible undo, `storeErrors.notice` is a banner
*after* the swap, and every recovery that has actually happened on this Mac was done
by hand and worked.

- `absent`, `usable` → open. Say nothing.
- `unreadable` → touch nothing. Flag the reason, let `SessionStore()` fail into the
  existing in-memory fallback and its banner. Retry next launch. A lock or a full disk
  heals; a restore does not give back the minutes it drops.
- `damaged` / foreign → still touch nothing. Modal at launch naming the reason, the
  newest *usable* backup, its age and its session count: **[Restore that backup]
  [Open Backups folder] [Continue without restoring]**. Only button one stages and
  applies. Button three runs in memory and never writes over the damaged file.

`AppModel.init` therefore cannot own this. Extract `StoreBootstrap.plan(storeURL:
backupsDir:) -> Plan` — pure, no mutation — and let `AppDelegate` act on the plan.
README's "restored automatically" sentence is now false and must change with the code.

### 3. Restore selection

Match by content, never by name. The source store in a backup folder is the entry
matching `*.store` (excluding `-wal`, `-shm`, `manifest.json`) that passes §1 as
`usable`. Several candidates: prefer the live store's own name, else the largest.
Sidecars follow the chosen stem and are renamed to the live name during staging.
This opens all twelve folders the owner has — `default.store`, `timex.store`,
`billing.store` alike. Automatic candidate selection iterates newest-first and skips
any folder whose store is not `usable` (quality's fallback loop, granted). The
confirmation must print folder stamp, internal file name and `count(*)` from
`ZWORKSESSION`; that count is how the owner tells a real backup from a harness one.

### 4. Harness quarantine

`AppModel.backupsDir` becomes derived, not absolute:
`StorePath.url().deletingLastPathComponent().appendingPathComponent("Backups")`.
One quarantine gate for store and backups; `CUTAWAY_SCENARIO` stops being a second,
weaker gate. The five existing `timex.store` folders are the **owner's** files — the
app never deletes what it cannot classify, and that rule stays. Remove them by hand
before rotation acts, and add the check to the release list. Rotation stays pure on
names.

### 5. Retention and litter

- The oldest surviving generation is never evicted. One line in `survivors`; ~800 KB.
  Without it `billing-20260823-122952` — the pre-incident copy — dies on 2026-09-22.
- Newest-`keep` and newest-per-day for 30 days stand as written.
- `.replaced-*`: keep the newest always, delete the rest past 30 days, at launch.
  `.staging-*` past 24 h likewise.
